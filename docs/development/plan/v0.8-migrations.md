## 2. R-LABEL-17: province, city and district as printed

[reviews/label.md](../../reviews/label.md) has the four layouts and where each prints the area. Read them

Fixtures: add the area to the label PDFs `cargo run -p packing-fixtures` writes (made-up places only,
for example `JAWA BARAT,KAB. CONTOH,CONTOH TENGAH`), and a table test per layout. The samples baseline is
re-pinned only after checking that only the new fields changed.

## 3. R-APP-16 and D-APP-33: the start screen, the migrations, read-only

[reviews/app.md](../../reviews/app.md), [D-APP-33](../../software-design/decisions/app.md), and the rule in
`AGENTS.md`.

- At start, the app finds what needs migrating in the data folder: dates whose `session.toml` is of
  another `schema`, and batches saved before step 2 with no area recorded.
- If anything does, it asks before any date opens: what would change (which dates, how many batches),
  with **Update** and **Open read-only**. This is the only way into read-only.
- **Update** runs the migrations and shows its progress line by line, for example *Reading addresses:
  2026-11-25, batch 1, page 3 of 120*. The back-fill reads each batch's stored input PDFs and appends
  one record per batch, never an edit. Then the views are written again (schema 2.1).
- **Read-only** writes nothing at all: no migration, no `.partial` recovery, no view, no lock-holder
  file, no batch, revert, amend, reprint, mark or summary. The screens show it is read-only, and the
  actions that would write are not offered.
- Follow the owner's UI rules in memory: buttons are one short verb; a question's line says the
  consequence; no text ends in `…`; the screen looks like Settings, Plan and Day.
- Update the design: [journal](../../software-design/data/journal.md) (When a date opens),
  [views](../../software-design/data/views.md), the record's fields, and the
  [user guide](../../user-guide/README.md) (the start question, read-only).
